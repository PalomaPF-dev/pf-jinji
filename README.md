# PF人事管理（paloma-pf-jinji）

生産・調達統括本部の**人事マスター**。人事情報の原本を持ち、組織図の形成・異動申請書の作成・
人事考課・基本給与・資格までを一元管理する、**管理者専用**の社内業務アプリ。
PFシリーズ（ポータル `pf-portal` 配下）の一員として、ポータルの部署マスターおよび
SSO・権限の枠組みと連動する。

## 機能

1. **人事マスター** — 社員台帳（社員番号・氏名・カナ・性別・生年月日・入社日・雇用体系・所属・役職・職務・等級・在籍状態・退職日・連絡先）。検索／所属・在籍状態での絞り込み、CSV入出力。年齢と勤続年数は保存せず生年月日・入社日から都度計算する。
2. **組織図の形成** — 実物の配置表と同じ様式（階層ごとに列を分け、部署／氏名／役職／職務 を並べる）。人は自分の所属組織の深さの列に出る。ツリー表示にも切り替えられる。基準日を指定した表示と印刷。
3. **異動案の編成** — 組織図の上で人をドラッグして配置を組み替える。動かしても人事マスターは変わらず「案」に溜まり、確定すると対象者ぶんの異動申請書が起案される。◎昇格（職務・役職）／○昇格（職務）／△所属移動 の印が付く。
4. **異動申請書** — 指定帳票 **J-426(9)「異動申請書 ・ 組織名称追加変更申請書」**。起案→申請→承認→発令の一連。承認が揃うと人事マスターと組織図へ反映される。暦年連番（`J26-001`）で採番し、A4縦1枚の帳票として印刷できる。
5. **継続雇用申請書** — 指定帳票 **J-456「高齢者雇用・アルバイト契約満了に伴う継続雇用申請書」**。契約満了に伴う期間限定の継続雇用を申請する。年齢と実働時間は生年月日・勤務時間から自動計算する。
6. **人事考課** — 評価期（年度＋上期/下期）ごとの一次・二次評価。総合評価を入れて確定すると以後変更できない。項目マスターは設定画面で確認できる。
7. **基本給与** — 改定履歴を積み上げる履歴型。最新の有効行が現在の給与。取り消しは行を消さず無効化する。
8. **資格** — 保有資格と有効期限。期限までの残り日数を色分け表示し、期限接近を日次で点検する。
9. **ポータル連携** — この人事管理を「人」のマスターとして、所属・役職・人事情報をポータルへ送る。異動の発令が各業務アプリの部署・権限まで届く。
10. **設定** — 利用許可名簿・資格マスター・考課項目・監査ログ（責任者のみ）。

## アクセス制御

人事情報は本部で最も機微なデータのため、**二段構え**にしている。

| ゲート | 内容 |
|---|---|
| 1. ログイン | 社員番号＋パスワード（next-auth）、またはポータルからのSSO（`/api/sso`） |
| 2. ポータルの管理者権限 | ポータルで**管理者（role=admin）またはポータル管理権限（can_manage）**を持つ人だけがアプリを使える。満たさない社員番号は、ログインできても `/forbidden` |

ポータル側でも二重に絞っている。人事管理のタイルは管理者にしか出ないうえ、
起動URL（`/api/user?launch=jinji`）を直接叩いても管理者でなければ 403 になる。

### 名簿は「どこまで見られるか」を決める

`jinji_admins` は入室条件ではなく、**入れた人がどこまで見られるか**を決める。

- `is_owner` — 名簿・各種マスターを編集できる（人事の責任者）。給与・考課も常に閲覧可
- `can_payroll` — 基本給与の閲覧・編集
- `can_evaluation` — 人事考課の閲覧・編集

名簿に無いポータル管理者も、人事マスター・組織図・申請書・資格までは扱える。
**給与と人事考課はポータル管理者でも自動では開けない**（名簿で個別に許可する）。

ただし `is_owner` は入室も許す。責任者を締め出すと名簿そのものを直せなくなり、
アプリが誰にも管理できない状態に陥るため、ここだけは逃げ道を残してある。

権限判定は**毎回 DB を引く**（JWT には載せない）。ポータルで管理者を外した瞬間から、
手元に残っているセッションでも操作できなくなる。ポータルの権限は SSO と
プロビジョニングの両方で届き、`users.role` / `users.can_manage` に保存される。

さらに、給与・考課は**閲覧も**監査ログ（`jinji_audit_logs`）に記録する。

## 公開URL

本番は **https://jinji.paloma-pf.com**。他のPFアプリと同じ `paloma-pf.com` ゾーンに置く。

ポータル（`portal.paloma-pf.com`）とはホストが違うためクッキーは共有されないが、
`/api/sso` へのトップレベル遷移でこのホスト自身にセッションクッキーを発行するので、
SSOはそのまま動作する。Vercel 側でドメインを割り当てたうえで、`NEXTAUTH_URL` を
同じURLにすること（パスワード設定リンクの生成にも使うため）。

本番へ出す手順は [docs/deploy.md](docs/deploy.md) にまとめてある。

## 技術スタック

- Next.js 16（App Router／Server Components＋Server Actions）
- Neon Postgres（**pf-jinji 専用DB**。給与・考課を他アプリのDBから物理的に分離）／ node-postgres（`DB_DRIVER` 自動判定）
- next-auth v4（社員番号＋パスワード／JWT。クッキー名はアプリ固有 `jinji.session-token`）
- Tailwind CSS v4 / lucide-react / 共通UI `@paloma-pf/ui`（AppShell）

## 開発

```bash
npm install
npm run dev        # http://localhost:5190
npm run typecheck
npm run lint
npm run build
```

`.env.local` は [.env.local.example](.env.local.example) を参照。最低限 `DATABASE_URL` と
`NEXTAUTH_SECRET` があれば動く。テーブルは初回アクセス時に冪等作成される（`src/lib/schema.ts`）。

初回は利用許可名簿が空のため `/setup` に誘導され、最初の1人（owner）を登録する。
`JINJI_BOOTSTRAP_ADMIN_IDS` を設定した環境では、その社員番号が owner として自動登録される。

以後の利用者は設定画面（`/settings`）から名簿に追加し、「設定リンクを発行」で
パスワード設定用のリンクを渡す（メール送信は持たない）。

### 運用の始め方

1. `/setup` で責任者を登録
2. `/org/edit` でポータルの部署を同期し、本部→部→課→係の階層を組む
3. `/employees/import` で社員をCSV取込（ポータル連携が未整備でもここだけで始められる）
   - 試すだけなら [docs/sample-employees.csv](docs/sample-employees.csv) をそのまま取り込める
     （所属コードはポータル既定の D001・D002・D003・F001・W001 を使っている）
4. 以後の所属・役職の変更は `/transfers` の異動申請書から行う（履歴が残る）
5. `/settings` の「ポータル連携」で、人事情報をポータルへ送る

## ポータル連携

### どちらがマスターか

| 情報 | マスター |
|---|---|
| 氏名・所属・役職・職務・生年月日・入社日・雇用体系・在籍状態 | **人事管理** |
| 組織の階層（本部→部→課→係）・組織の長 | **人事管理** |
| ログインID・パスワード・アプリ権限（role / can_manage / apps）・承認者 | **ポータル** |
| 部署・職場そのものの存在（コード・名称） | **ポータル** |

人事管理は**パスワードも権限も送らない**。ポータル側の権限運用は壊れない。

### 流れ

```
人事管理で異動を発令
  → ポータルへ所属を連携（POST /api/hr-sync）
  → ポータルが各業務アプリへ再連携
  → 各アプリの部署・権限が追従する
```

設定画面の「ポータル連携」から全件をまとめて送ることもできる。送信前に
「連携内容を確認」で中身を点検できる。ポータルが落ちていても発令そのものは成立し、
あとから連携をやり直せる。

### このアプリ側（実装済み）

| 経路 | 内容 |
|---|---|
| `GET /api/sso?token=…` | ポータルからのSSO。`PF_PROVISION_KEY` で HMAC 検証。ポータルの `role`・`canManage` を保存し、管理者でなければ `/forbidden` へ |
| `POST /api/provision` | ポータルからの一括アカウント発行（PFシリーズ共通契約 v2.1）。`canManage` も受け取る |
| 部署マスター取込 | ポータルの公開 `GET /api/departments`・`/api/workplaces` を取り込み、組織ツリーへ upsert |
| ポータルへの人事情報連携 | ポータルの `POST /api/hr-sync` へ送る（設定画面＋異動発令時に自動） |

### ポータル（`pf-portal`）側に必要な変更

`jinji` をポータルのアプリとして登録するには、ポータル側で以下の追加が必要（このリポジトリの範囲外）。

| ファイル | 変更内容 |
|---|---|
| `lib/db.js` | `ALL_APP_KEYS` に `"jinji"` |
| `lib/appUrls.js` | `APP_BASE_URLS.jinji = "https://jinji.paloma-pf.com"` |
| `lib/provision.js` | `PROVISION_APP_KEYS` に `"jinji"` |
| `api/user.js` | `SSO_APP_KEYS` に `"jinji"`／`ADMIN_ONLY_APP_KEYS` で管理者以外の起動を拒否／トークンに `canManage` |
| `lib/provision.js` | プロビジョニングの送信内容に `canManage` |
| `lib/userProfile.js` | セッション応答に `role`（タイルの出し分け用） |
| `index.html` / `admin.html` | `APPS` にタイル定義、`SSO_APPS` に追加 |
| `icons/jinji.png` | タイル用アイコン。本リポジトリの `public/icon-192.png` をそのままコピーする |
| `api/hr-sync.js` | **人事情報の受け口（新規）**。仕様と参照実装は [docs/portal-hr-sync.md](docs/portal-hr-sync.md) |
| 部署マスター | **管理者部署（D999 等）にだけ** `jinji` を割り当てる |

上記が入るまでの間も、本アプリは自前ログインとCSV取込だけで完結して運用できる。

## 指定帳票

受領した実物のExcelに合わせて2種類を実装している。どちらも**A4縦1枚**に収まる。

| 帳票 | 内容 | 画面 |
|---|---|---|
| **J-426(9)** | 異動申請書 ・ 組織名称追加変更申請書 | `/transfers` |
| **J-456** | 高齢者雇用・アルバイト契約満了に伴う継続雇用申請書 | `/reemployments` |

### J-426(9) について

1枚で「人事異動」と「組織名称の追加変更」を兼ねるため、作成時にどちらとして起票するかを選ぶ。
組織名称として起票した場合は異動日付・異動部署の入力を求めない。

チェック欄（転居・住居・赴任形態・単身赴任事由・携帯・社用車・駐車場・通勤経路変更）は
**あえて必須にしていない**。実物は手書きでㇾ点を入れる欄なので、空欄のまま印刷して
用紙に書き込む運用も残せるようにしてある。ただし矛盾した組み合わせは作れない
（転居「なし」なら住居欄を出さず、送られてきても保存時に落とす）。

決裁は帳票右下の【承認】枠＝**申請者・部門長・役員**の3つで、揃うと発令できる。
左の枠（総務人事部長・情報ｼｽﾃﾑ部・人事統括室）と【総務人事部使用欄】は決裁後の回付を
記録する枠なので、アプリでは押印用の空欄として印刷するだけにしている。

### J-456 について

年齢（契約満了日時点の満年齢）と実働時間（勤務時間−休憩）は入力させず、
生年月日・勤務時間から計算して帳票へ入れる。人が二重に書いて食い違うのを防ぐため。

雇用形態は実物が「高齢者雇用（有期契約）継続　・　アルバイト雇用契約」と両方を刷って
該当を選ぶ形なので、選ばれた側に下線を引いて印刷する。

この帳票は**承認までで完結**し、人事マスターへの自動反映は伴わない
（雇用形態や契約満了日を実際に書き換えるのは人事マスターの編集画面の役割）。

### レイアウトを直すとき

- `src/lib/types.ts` — チェック欄の選択肢・承認枠の並び・固定文言
- `src/lib/transferForm.ts` — J-426(9) のタイトル・注記・対比項目・採番
- `src/app/transfers/[id]/print/page.tsx` / `src/app/reemployments/[id]/print/page.tsx` — 用紙上のレイアウト

入力欄・DB・一覧・詳細はいずれもこの定義を参照している。

## 検証

実DB（PostgreSQL 16）と実ブラウザ（Playwright）で、各段階を通しで確認している。

```bash
npm run typecheck && npm run lint && npm run build
```

確認済みの主な観点:

- ポータルの一般社員は、ログインできても全ページ・CSV出力APIから締め出される
- ポータルで管理者を外すと、既存セッションでも次の操作から即座に効く
- ポータル管理者でも、名簿で許可しなければ給与・考課は開けない
- ポータル側でもタイルを出さず、起動URLを直接叩いても管理者以外は 403 になる
- `can_payroll` / `can_evaluation` が無ければ給与・考課は開けず、拒否画面に金額も漏れない
- ポータル同期は名称だけ取り込み、人事側で組んだ階層を壊さない
- 異動の発令は人事マスター更新と状態更新が同一トランザクションで、二重発令もできない
- 給与は履歴が積み上がり、取り消すと1つ前が現在値に戻る
- 最後の責任者（owner）は名簿からも権限からも外せない
- 発令するとポータルの所属・役職まで自動で連携され、所属が変わった人だけ各アプリへ再連携される
- ポータルが落ちていても発令は成立し、人事マスターへの反映は失われない
- 連携でパスワード・アプリ権限・承認者は送られない
- 指定帳票2種がどちらもA4縦1枚に収まり、入力した内容がそのまま帳票に出る
- 帳票のチェック欄は連動する（転居なし→住居欄なし、単身赴任→事由欄あり 等）
- 入力エラーで差し戻されても、複数チェックを含めて書いた内容が消えない
- 組織図でドラッグして人を動かしても人事マスターは変わらず、案に溜まるだけ
- 案を確定すると異動申請書が起案中で作られ、そこから先は通常の承認・発令の流れに乗る
- 申請書を作っただけでは人事マスターは変わらない（発令して初めて反映される）
